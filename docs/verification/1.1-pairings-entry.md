# Version 1.1 pairings and folder entry verification

October 27, 2026. This slice implements the pairing and Mac entry work in the [1.1 plan](../plan-1.1.md#implementation-status). It is development evidence, not release approval.

## Implemented behavior

Saved pairings support search across name, folder label, repository, and destination. Every search term must match; matching is localized and case/diacritic insensitive. Rename preserves identity, bookmark, route, and filters. Pinning places pairings first; Move up/down changes order within the pinned or unpinned group. The options menu exposes these actions and removal. New pin/order fields decode with defaults for older archives, retaining their original array order until edited.

Applying or saving a pairing records a live active-route binding. It compares the resolved source directory's device/inode identity, repository kind/name, destination, and filters. A different folder at the same display path cannot match. Manual configuration divergence clears the binding; returning fields to their old values does not reactivate it. Names, pinning, ordering, and repository visibility are not route identity. Bookmark restoration supplies the source URL; invalid bookmarks do not fall back to an unrelated path. Late pairing selection responses cannot activate a newer workspace configuration.

Folder picker, window drops, and AppKit open events use the same capture and staging path. Capture retains security-scoped access and bookmarks before deferred presentation. Symbolic-link URLs resolve to the target while the original grant remains held; the resulting bookmark is acquired independently before that grant is released. Duplicate folder identities are collapsed. Multiple folders present a chooser instead of silently taking the first. Files, packages, and nonlocal URLs reject the entire selection with an explanation.

Replacing an existing prepared workspace requires an explicit choice. An open dataset-card editor or upload review blocks replacement, preserving its work. Reentrant open events cannot replace a workspace during its confirmation prompt. Folder entry never starts an upload or changes existing queue items. Cancelled selection releases its retained folder entries. A chosen folder retains the existing destination and filters, matching the prior folder-picker behavior; a pairing supplies its own route and filters.

The application registers `public.folder` as an alternate Viewer in its generated Info.plist, including inherited Store configuration. The AppKit delegate captures cold-launch events before the model attaches; once the window attaches it delivers retained entries once. Warm events ask the scene's open-window action to show the workspace. Registration does not make Face Hugger the default folder handler.

## Automated and visual checks

`Scripts/check.sh --build` passed:

| Check | Result |

| Swift XCTest | 64 passed |

The ten pairing tests include seven new tests covering legacy defaults and metadata round trips, route-preserving edits, search, stable mixed-record ordering, folder identity through moves and symbolic links, same-path replacement, route/filter mismatch, binary UTF-8 destinations, multi-folder capture/deduplication, bookmark restoration after closing original scopes, and refusal of mixed files/packages/remote URLs. Existing folder-access tests continue to cover balanced scope lifetimes and stale/invalid bookmark handling.

The actual pairing picker and folder-selection SwiftUI views were rendered and inspected in light and dark appearances. Fixtures include Unicode names, long names/routes, pin and active indicators, multiple folders, and long local paths. These previews do not load the real app's queue, credentials, or pairings. The generated Debug app's Info.plist was inspected for its folder document type, alternate rank, executable, bundle identity, and macOS 15 minimum.

A native open-event smoke used the actual `FaceHuggerApp.swift` scene, delegate, and window-reopening code with a synthetic model and minimal view. Launch Services delivered the cold-launch folder once after model attachment. The harness then closed its workspace window; a warm folder open delivered the second folder and reopened a visible workspace. The harness quit afterward. It used a unique temporary bundle ID and no real app state, credentials, or network requests. This verifies entry wiring, not the real model's confirmation prompts or sandbox access.

The universal Release executable passed per-architecture `lipo` checks, both slices report `minos 15.0`, its folder registration matches the Debug app, and its ad hoc signature passes strict verification. This is a development build and does not establish actual Intel execution, Store signing, or installer validity.

Local evidence: `.build/pairings-entry-check.log`, `.build/one-one-universal-build.log`, `.build/one-one-universal-inspection.log`, and `.build/pairings-entry-preview/` (rendering and native open-event harnesses, images, and `dock-smoke.log`).
